Every tag/module name below links straight into the generated rustdoc, and the diagram nodes are clickable too. Those links work after a local cargo doc build. The diagram itself needs internet (Mermaid CDN); everything else works offline. Gates that must stay green: cargo fmt --all --check · cargo clippy --workspace --all-targets -- -D warnings · cargo test --workspace.

⚠️ Naming trap: the forza-cli package has no library target — its [[bin]] name = "forza" in Cargo.toml — so Cargo doc generates target/doc/forza/, not target/doc/forza_cli/. Every other crate's doc folder matches its package name (dashes → underscores); this one is the sole exception.

🖥️ forza-gui + ⌨️ forza-cli top

GUI (Slint): Tokio runtime on a dedicated thread; callbacks only enqueue over mpsc, results come back via invoke_from_event_loop. State in ui_state.rs, handlers in callbacks/*, read-model mapping in detail_views.rs, window geometry/tab persistence in ui_persist.rs, IO in worker.rs.

CLI (bin forza, package forza-cli): Clap; declares a dependency on forza-gui (launch/reuse) — the binary is never lightweight.

🧭 Modularization assessment

Evaluated against the generated target/doc tree + each crate's Cargo.toml, not just this diagram.

SignalVerdictWhy
Layered DAG, 0 cyclessolidConfirmed: no crate's Cargo.toml creates a back-edge into a lower layer. forza-domain has zero internal deps, as a base crate should.
Domain is IO-freesolidNo filesystem/network/GUI/DB imports found in forza-domain/src. Business rules stay testable without a database.
Single hub for GUI+CLI use casessolidforza-app::services is the only place extraction/review/export logic lives — the GUI and CLI both call into it rather than each reimplementing use cases, which is the pattern most apps with two front-ends get wrong.
forza-cli → forza-guiwatchThe only sideways/upward edge, and intentional (the CLI's gui subcommand launches the same window). But it means every CLI invocation — including headless ones like forza export on a server — links Slint and its native toolkit deps. A feature = "gui" gate on that dependency (default-on for the shipped binary, off for a minimal/headless build) would let this stay convenient without forcing the coupling on everyone.
Package name ≠ doc/binary name (forza-cli → forza)watchNot a design flaw — "forza" is the right name for the shipped executable — but it's an undocumented trap for anyone writing rustdoc links, cargo doc tooling, or onboarding docs (this page had a broken link to forza_cli/ before this revision). Worth a one-line callout in CONTRIBUTING/README, not a restructure.
forza-app::services flat namespace (15 siblings)watchAll 15 use-case modules sit directly under services:: with no grouping. At this size it's still scannable, but it's already large enough that services::images::{inventory, detail, debug, rename}, services::extraction::{runner, replay, discovery_plan}, and services::runs::{control, log} would cut cognitive load without changing any behavior — worth doing before it grows further, not urgent now.
forza-domain scope: rules + text-matching toolkitwatchAlongside racing-specific rules (lap, ordering, frontier, race_class, review_rules) the crate also carries a generic fuzzy-text-matching toolkit (difflib, normalizer, text_utils, car_names) plus embedded static reference_data. All of it is still IO-free so the layering rule holds, but conceptually it's two responsibilities in one crate. Not worth splitting today; worth remembering if difflib/normalizer ever get reused outside a racing context.
BestLapRow in forza-app, trait LapRow in domain::orderingsolidDomain must not reference the concrete struct (would be a cycle). The trait is the contract, the struct is the implementation — correct direction.
forza-db::test_support in public docsdoneWas shipping test helpers in the public API surface (seed_demo_database with no gate). Now #[doc(hidden)] with a comment explaining why: integration tests in two crates link against it, so #[cfg(test)] can't reach them and a cargo feature would force every cargo test invocation to opt in. Out of the documented API, zero build-matrix churn.

Net assessment: the layering and the GUI/CLI-share-one-orchestrator decision are the two things most projects this size get wrong, and this one gets them right. The items above are refinements for a codebase that's already past the stage where most modularization damage happens, not red flags.
